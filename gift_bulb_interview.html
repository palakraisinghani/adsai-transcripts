"What if the model calls suggest_ideas with the wrong recipient?" - What can happen: the tool takes optional recipient_id and maker_id. The model's value wins over the chat's current one (recipient_id or d.recipient_id). So the model can pick another saved person. - What can't happen: the model can't see anything unsafe. An id that doesn't exist makes pipeline.suggest raise LookupError. The tool catches it and returns {"error": …}, and the model sees that and can correct itself. - What still applies: the safety filters run on whichever person was chosen, using that person's allergies and the maker's age and skills. A wrong choice gives a wrong-person suggestion, but never an unfiltered one. - Honest weakness: the tool doesn't check that the model's id matches the person the user is chatting about. A fix would be to ignore model-supplied ids unless the user changed the person, or to make list_profiles the only way to switch. 2. "Why not let the model rank the ideas?" - Ranking uses private data: learned taste scores, past gifts, recent shows, difficulty fit and cost. A rule-based ranker is the same every time and testable. A model's ranking isn't. - Cost and latency: every ranking would be another model call on a free tier with a small daily budget. - Safety: ranking comes after the filters. A model ranking the survivors adds style, not safety. - What the model does do: it explains the pick in one or two sentences and decides which tool to call. In the non-chat path, personalize writes a "why it fits" line for ideas that rules already chose. 3. "How is this different from just a RAG app?" - RAG retrieves text passages by similarity and has the model write an answer from them. - Here, retrieval is structured queries and rules, not embeddings. The agent calls tools that return typed, validated results, such as ideas that pass filters and costs from the price table. - The agent also acts: it can save a researched idea, record a preference, or plan a gift. RAG only reads. - The output is validated against a schema, so every card on screen traces to a tool result. - Honest nuance: the web research part is closer to RAG. It fetches pages and has the model extract ideas, grounded in the page text, with the URL kept as the source. 4. "What happens if two tool calls conflict?" - The tools share one dependency object (Deps) for that run, holding the cards found so far and the actions taken. The write tools are also limited, with at most 2 online ideas saved. - Calls happen in sequence in one run, not in parallel, so there are no race conditions inside a run. Across runs, the database handles it. - The honest gap: the model could save an idea or plan a gift twice. A fix would be idempotency keys. 5. "What is the failure mode you're most worried about?" Turn 4

what about how to tune the likings for user
Claude's response
Searched for 1 pattern, ran 1 shell command
Likings are tuned in two layers: what the user states, and what the app learns from feedback. Both feed the ranking score. 1. Stated likes and dislikes (explicit) - Each recipient has likes, dislikes, allergies and cultural_notes. The user edits them on the profile page. - Likes are free text, such as "cats" or "football". core/likes.py matches them loosely: plural and stem matching, then a concept map. For example, "animals" points to cat, dog and panda tags, and "sports" points to football and cricket. - Colours and craft materials, such as "pink" or "ribbons", count as style or palette, never as the subject of a gift. They decide how something looks, not what it is. - In ranking, each matching like adds +1.5 and each matching dislike subtracts 2.0. A disliked material also subtracts 2.0. - Allergies and cultural "avoid" notes are hard filters, not scores. They remove ideas entirely, and no learned taste can override them. 2. Learned taste (from feedback) - After a gift, the user rates it 1–5 and can add reactions. - The rating becomes a score change for each tag of the gifted idea:
┌────────┬────────┐ │ Rating │ Change │ ├────────┼────────┤ │ 5 │ +2.0 │ ├────────┼────────┤ │ 4 │ +1.0 │ ├────────┼────────┤ │ 3 │ 0 │ ├────────┼────────┤ │ 2 │ −1.0 │ ├────────┼────────┤ │ 1 │ −2.0 │ └────────┴────────┘
- Reactions add to this: "loved it" and "used it" +1.0, "displayed it" +0.5, "not their style" −1.5. The total is capped between −3 and +3 per gift. - These changes are stored per recipient and per tag in recipient_prefs. Each score is clamped to −10…+10. - In ranking, the learned score is added at weight 0.5 for each tag. 3. Forgetting (decay) - Scores decay exponentially with a half-life of 180 days (PREF_HALF_LIFE_DAYS). A taste from six months ago counts half as much. - The decay is applied each time the score is read or updated, so old data fades without a cleanup job. 4. User control On the person's profile page, the learned tastes show as "loved" and "disliked" lists. Tastes weaker than 0.5 are hidden as noise. For each one the user can: - forget it, which deletes the learned tag; - like or dislike it, which pins it into the stated lists and stops it being treated as a guess. 5. With no profile The Default profile, which is what the new "just ideas" mode uses, has no taste of its own. It borrows what most people like on that occasion: diyas and lanterns for Diwali, balloons and cake for birthdays. How to say it in an interview "Stated preferences are hard constraints and strong signals. Learned preferences are a small, slowly decaying adjustment from ratings, so one bad gift can't permanently ban a style, and the user can always see and override what the system believes." Weaknesses a professor may press on - The tag-level update spreads one rating across all of an idea's tags, so the signal is blunt. A Bayesian or bandit approach would handle credit assignment better. - The weights (1.5, 2.0, 0.5) are hand-set, not tuned on data. - Ratings are sparse for gifts, so learning is slow. That's why stated likes dominate. Want me to add this as sample answers to the interview prep, or suggest how you'd improve the learning (for example with a bandit)?
